Implementación del sistema de mentorías

Fernando Astudillo Osorio · Grupo 5 · 19 de noviembre de 2026

La aplicación permite gestionar mentores, mentoreados, mentorías y sesiones. La versión actual se conecta con Supabase para autenticar usuarios, guardar registros y administrar archivos privados. Este documento resume la arquitectura implementada, los controles comprobados y las limitaciones que siguen abiertas.

Interfaz y flujo de uso

El administrador revisa el resumen y organiza las personas y mentorías. El mentor trabaja con sus sesiones y su perfil; el mentoreado consulta su información. Las fichas muestran primero los datos principales y despliegan la edición cuando se necesita. Cada sesión se abre por separado, y el botón Guardar cambios permanece visible durante el recorrido.

Arquitectura y datos

Arquitectura implementada

Usamos cliente-servidor con separación por capas. React y TypeScript presentan la interfaz; el dominio prepara los cambios y el repositorio adapta el acceso a Supabase. Vinext y Vite generan la aplicación y un Worker entrega su configuración pública.

Procedimientos · RLS · Restricciones

Esta implementación reemplaza la propuesta de un servidor Express por servicios administrados. El demostrador Node y SQLite del trabajo anterior se conserva como antecedente; no es el backend de la web actual.

Modelo de datos

Mentores y mentoreados se relacionan mediante mentorías. Cada mentoría tiene seis sesiones, y cada sesión admite una foto y un documento. Las claves foráneas preservan las asociaciones; las restricciones únicas evitan duplicar el número de sesión o el tipo de evidencia. Los archivos se almacenan en Storage y sus metadatos en PostgreSQL.

app_profiles vincula las cuentas con sus roles. audit_events registra operaciones y write_limits controla la frecuencia de escrituras. Las especialidades se conservan como una colección text[]; no se afirma normalización estricta de ese atributo. Un catálogo compartido requeriría una tabla de especialidades y otra de asociación.

Procedimientos almacenados

La aplicación invoca get_workspace(), que ejecuta CALL read_workspace para extraer datos bajo RLS. Para guardar utiliza save_changes(), que ejecuta CALL apply_changes. El segundo procedimiento valida privilegios, campos, versiones y restricciones; si una operación falla, revierte el lote completo.

Seguridad y configuración

Controles aplicados

ControlImplementación observada
AccesoSupabase Auth, perfiles activos y autorización RLS. El selector de roles solo funciona en la demostración.
Frecuencia10 solicitudes de registro/inicio de sesión por 5 minutos e IP; 120 lotes de escritura por minuto y cuenta.
TokensAcceso válido por 3600 segundos. Detección de reutilización de refresh tokens activa, con intervalo de 10 segundos. La renovación no limita la duración total de sesión.
ArchivosBucket privado, enlaces de 15 minutos, fotos de hasta 2 MB y PDF de hasta 5 MB. Firma en cliente y controles MIME/tamaño en Storage y SQL.
IntegridadCampos permitidos, transacciones, control de versiones y auditoría. Secretos excluidos del repositorio.

La sesión única y los límites de duración e inactividad del servidor están restringidos al plan Pro en el proyecto observado. Permanecen pendientes; no se contrataron servicios de pago. El sistema tampoco incorpora análisis antivirus de archivos ni limpieza automática de objetos huérfanos.

Entorno de ejecución

El equipo de desarrollo utiliza Windows 11, Intel Core 5 210H, 12 procesadores lógicos y 7,6 GB de RAM utilizable. Supabase utiliza el plan gratuito con cómputo Nano en West US Oregon. El proveedor administra ese hardware; no se declara instalación de equipos físicos nuevos.

Para reproducir el entorno se requiere Node 24, ejecutar npm ci, configurar SUPABASE_URL y SUPABASE_PUBLISHABLE_KEY y ejecutar npm run dev. El servidor local utiliza localhost:3000; Supabase se conecta por HTTPS/443. El script de migración y el alta del primer administrador están en supabase/.

Verificación y alcance

Resultados comprobados

La instalación con npm ci en una copia limpia y la compilación terminaron correctamente. TypeScript y lint aprobaron, al igual que las 32 pruebas automatizadas. De ellas, 18 pertenecen al demostrador anterior; las restantes cubren reglas del cliente y una migración PostgreSQL ejecutada con PGlite.

En la interfaz actual se verificaron el acceso real, la apertura de fichas y sesiones, y el guardado de un resumen contra Supabase. Las verificaciones previas incluyeron creación de personas y mentorías, generación de seis sesiones, carga de fotos y PDF, exportación Excel y aislamiento entre los roles Mentor y Mentoreado.

Aspectos pendientes

La emulación móvil no aplicó el tamaño solicitado, por lo que su verificación queda pendiente. No se han realizado pruebas de carga, restauración de respaldos ni una auditoría completa de accesibilidad. La configuración de sesiones del servidor requiere resolver la limitación del plan gratuito. Estas restricciones deben considerarse antes de declarar el sistema preparado para producción.

La versión publicada conserva el acceso privado del sitio; su enlace no concede acceso automáticamente al docente. El README del repositorio registra la arquitectura, instalación y estado de publicación vigente.
